## 4. Comprehensive Analysis

### High-Confidence Findings (where convergence means reliability)

The three models converge on the **single most important architectural decision** with unusual unanimity: implement a **client-side set-union merge over the existing LWW transport** rather than adopting `SYNC_CONTRACT.md` §7's destructive default. Claude Opus 4.8 proves the safety algebraically (per-cell set union is a bounded join-semilattice — a state-based G-Set CRDT — and therefore commutative, associative, and idempotent), Gemini 3.1 Pro frames it as "CRDT principles applied onto a legacy REST endpoint without modifying the server," and GPT-5.5 frames it as "wire-compatible LWW with a safe local-merge guard." All three independently observed that because `data[dateKey][categoryId]` is a *set* of indices, the merge output is byte-identical in shape to what the web app would write — so the deviation is a strict refinement, not a fork, of the §7 protocol. When three frontier models reach the same architectural answer from different angles, that is strong evidence the answer is right.

Equally convergent: **auth should reuse the existing JWT email/password backend; magic-link is the runner-up and is deferred; SIWA/Google is rejected** because App Store Guideline 4.8 would force Sign in with Apple as a companion requirement, dragging in native SDK risk and entitlement management for zero meaningful benefit on a demoted hobby tracker. All three also converge on the **401-handling rule** that does the most work for safety: a 401 triggers exactly one silent refresh-and-replay; refresh failure produces a "needs re-auth" state that **preserves all local data**; `clear()` is only callable from the explicit logout path. This rule, more than the merge math itself, is the direct inversion of the Creighton/Chart35 silent-logout failure mode.

A third area of agreement is the **catalog/date fix-first ordering**. All three insist that [`CategoryCatalog.kt`](https://github.com/JacobStephens2/daily-dozen-kmp/blob/master/composeApp/src/commonMain/kotlin/page/stephens/bountywell/domain/CategoryCatalog.kt) must be replaced with 13 hyphenated IDs including `protein`, the 5 diet presets must be added, and date keys must be JS `toDateString()` in device-local timezone — all *before* any sync code is wired up, because every underscored ID or missing `protein` is a silent divergence between web and KMP that no merge layer can repair. Likewise the persistence model: all three abandon the count-based SQLDelight schema and move to `kotlinx.serialization` of the contract blob with explicit unknown-field passthrough, and all three agree the count→indices migration is `count = N → [0..N-1]`. The convergence makes this a low-risk, write-it-and-commit-it Milestone 0/1.

### Areas of Divergence (where the models thought differently)

The most consequential disagreement is **what logout does to local data**. Claude Opus 4.8 and GPT-5.5 hold the maximalist position: logout clears auth tokens only; local data persists unconditionally; deleting local data is a separate, clearly-labeled action. Gemini 3.1 Pro takes the mainstream position: logout wipes local data by default, with a "you have unsynced data, sync now?" pre-prompt. Given the explicit "no silent data loss, ever" mandate and the Chart35 precedent, the Claude/GPT-5.5 position is more defensible — a pre-prompt is still a destructive default, and a sleep-deprived user clicking through it reproduces the failure mode the brief was written to prevent. Recommendation: adopt the Claude/GPT-5.5 stance.

The second meaningful divergence is **un-check semantics** in the merge. Claude is the most algebraically honest: G-Sets are grow-only by definition, so an un-check on one device while another device has the index checked will see the index reappear after merge — documented as a deliberate trade and a 2P-Set/OR-Set deferred to a future version. GPT-5.5 keeps grow-only union but adds a user-visible "remote deletion not silently applied" conflict signal so the user can re-decide. Gemini gestures at OR-Sets with tombstones but doesn't commit. The right move here is Claude's grow-only union as the implementation, with GPT-5.5's contestability banner added on top — the merge stays correct and simple, but the user is told what happened.

The third divergence is **token-storage abstraction**. Gemini's `multiplatform-settings`-based approach is faster to ship and ecosystem-aligned; Claude and GPT-5.5 prefer a bespoke `TokenStore` expect/actual because it gives explicit control over iOS Keychain accessibility flags and a precise `clearAuthOnly()` semantic that mainstream wrappers blur. For Daily Dozen specifically — where auth handling is the critical-path mitigation for the data-loss failure mode — explicit beats convenient. Adopt a bespoke `TokenStore`; if scope tightens later, `multiplatform-settings` is a safe drop-in.

Finally, the **scope calibration** itself differed in tone. Gemini was the most optimistic about transferable value, listing three high-leverage skills. Claude was calibrated and prescriptive ("one ADR, then stop"). GPT-5.5 was the most unsentimental, going so far as to letter-grade the project ("B if capped, D if it becomes a product rabbit-hole"). The brief explicitly asked for honesty calibration, and GPT-5.5's grading is the closest match — keeping that grade in view is a useful forcing function against scope creep.

### Unique Insights Worth Noting

Three model-specific contributions stand out as genuinely additive. Claude's **algebraic proof of the merge's correctness** is the artifact that makes the §7 deviation defensible to a reviewer; it should be the centerpiece of the Decision-8 ADR. Claude's **Wasm in-memory-reload risk (D4)** is a real bug the other two missed and must be mitigated explicitly ("treat empty local as 'needs pull,' never 'authoritative empty to push'") or the Wasm build silently reproduces Chart35. GPT-5.5's **property-based merge tests as CI gates** is the cheapest mechanism for ensuring a future refactor cannot reintroduce the failure — promoting algebraic claims from aspiration to enforced invariant. Gemini's **specific library and timezone-pinning callouts** save investigation time and pre-empt the most likely "obvious bug" overcorrection a future reviewer would attempt.

### Recommendations

Adopt the union of the three plans with these specific tie-breakers: (1) **Sync model:** Claude's algebraic framing, GPT-5.5's property-based CI gates, plus the contestability banner for un-check divergence. (2) **Token storage:** bespoke `TokenStore` expect/actual per Claude/GPT-5.5; defer `multiplatform-settings`. (3) **Logout UX:** Claude/GPT-5.5's "auth loss is not data loss" — logout never wipes local data; deletion is a separate, opt-in action with honest local-only labeling because the backend exposes no delete endpoint. (4) **Wasm:** adopt Claude's D4 mitigation as a hard rule. (5) **Phasing:** GPT-5.5's atomic commit numbering inside Claude's 7-milestone granularity. (6) **Scope calibration:** keep GPT-5.5's letter grade verbatim ("B if capped, D if it becomes a product rabbit-hole") as the forcing function against scope creep, and ship the single ADR. (7) **Catalog/date/persistence:** all three converge, so just execute — these are Milestone 0/1 with no remaining decisions to make.

The honest summary all three models agree on: this work produces a real, transferable engineering pattern — offline-first cross-platform sync without data loss, a reusable KMP secure-token + Ktor refresh pattern, and data-dignity UX — and that pattern is worth exactly one published ADR. It should be capped at the smallest scope that delivers verifiable §9 round-trip parity. Build it, ship it, write the ADR, and stop.
